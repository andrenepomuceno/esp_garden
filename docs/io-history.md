# I/O history — append-only segments

`/hist0.bin` .. `/hist7.bin` hold the last N snapshots of every input and output. Records are appended to the END of the newest segment; when it fills, the oldest is truncated, stamped with a new sequence number and written into. **Nothing is ever rewritten in place — not a record, not a header** — because in-place mutation of a large file is what [panicked the board under LittleFS](filesystem.md). Flash usage stays bounded at `8 * (12 + recordsPerSegment * 48)` bytes forever.

- **The segment header carries NO record count.** The count is the file length. Storing one would mean rewriting the header on every append — reintroducing exactly the mid-file write this design removes — and would turn a torn append into a disagreement between two places instead of a short tail that does not divide evenly and is ignored.
- **Retention became granular, and that is the price.** A whole segment is dropped at once, so records held swing between `7/8` and `8/8` of capacity — at the default 1440, between 1260 and 1440.
- **Both parameters are config-driven**: `history.records` (0 disables the feature) and `history.periodSec`. `history.records` is the TOTAL, divided across the eight segments and rounded up, so the history is never shorter than what was asked for.
- **Nothing is preallocated any more.** Segments take space as they use it and release a whole segment at a time; after the first full cycle no new space is ever needed.
- **The record layout is fixed regardless of build flags.** A board with one probe still writes four moisture slots filled with NaN, which serializes as `null`. Making the layout depend on the fitted probe count would mean two firmwares disagree about how to read one file with no way to tell which wrote it. Each header carries `recordSize`, and a segment that disagrees is deleted rather than reinterpreted.
- **A `recordSize` disagreement is fatal to a segment. A CAPACITY disagreement is not, and until 2.20.0 it was.** The header also carries `records`, the segment's own per-segment ceiling, and `begin()` dropped and DELETED any segment whose value differed from the one derived from `history.records`. So editing the buffer size in `/devices.html` silently wiped every stored record at the next boot — on a garden whose whole moisture programme is waiting for long records. The two fields are not the same kind of thing: `recordSize` guards a FORMAT, where reading 40-byte records out of a 48-byte file returns plausible garbage, and a 48-byte record written into a 375-per-segment file is **byte-identical** to one written into a 1250-per-segment file. Capacity guards an eviction policy, and destroying an archive to enact a preference about how much of it to keep is the wrong trade in both directions.

  **Segments of different sizes now coexist, and converge by ordinary eviction.** A segment is full at `segmentFillLimit(own, target)` — the SMALLER of its own header and `recordsPerSegment()` for the capacity configured now — so an inherited slot is never written past its own header (which would lose its tail at the next boot, silently, because a too-long file and a corrupt one are the same observation) and never past the current geometry (which would take space `ioHistoryFitCapacity()` never credited, since that measured the files as they are today). A recycled slot is truncated and restamped with the new size, which is the existing rotation and not a header rewrite — the mid-file write that panicked this board is not re-introduced. Within one full cycle of the eight slots every segment carries the new size.

  **The index arithmetic needed NO change, and that is worth knowing before anyone "fixes" it.** `locate()` already sums `counts[]` per slot, `slotToRecycle()` and `buildOrder()` work off sequence numbers, and `forEach()` walks absolute ordinals corrected by `evicted()` — which counts the records a rotation actually discarded, whatever the segment held. Nothing above the fit check ever assumed uniform segments. What did assume it is `capacity()`, which was `segmentRecords * kSegments`; it is now `liveCapacity()`, the sum of the slots' own ceilings, because the product renders `Status.History` as **`12000 / 3000`** the day after a reduction.

  **Shrinking is the direction with a cost, and it is stated in the boot log rather than hidden.** Nothing is dropped at the change; the buffer holds more than the configured capacity until it converges, and each rotation during that drops a whole OLD segment — up to 1250 records at once rather than 180. **And if the point of the reduction was to free flash, the space comes back one segment per rotation and not at that boot**, where the old delete-everything rule returned all of it instantly. That is the one thing the previous behaviour did better, and it bought it by deleting the archive.

- **`history.records` is capped twice, and the two caps answer different questions.** The static ceiling in `ConfigFile::loadFile()` is **10000** and says what the RECORD costs: 480 KB of segment files once every segment has filled, LittleFS's 4 KB blocks included (`8 * ceil((12 + 1250 * 48) / 4096) * 4096 = 491 520 B`; the unrounded figure is 468.8 KB). It went 6000 → 5000 at 48 bytes, then 5000 → 2500 under LittleFS, then back to 5000 — and every one of those moves was somebody re-deriving one device's free space by hand and writing it down as a constant, which is necessarily wrong for every other device. **The 5000 → 10000 move in 2.20.0 is not another of those**: it is arithmetic about the record and nothing else, and what each board gets is decided below. On a WROOM-32 (device 6224's numbers) a request of 10000 resolves to **3408 records, exactly as 5000 did** — there the partition refuses, not the constant. On the S3 carrier's 2432 KB filesystem 10000 is **granted whole at 480 KB**, against a partition that would in fact hold 40 952. So the ceiling now binds on one family and is irrelevant on the other, which is the correct shape for a number about the record.

  What free space there IS is now measured. `ioHistoryFitCapacity()` runs at config load, adds the bytes the current segments hold back to the free space (the new capacity replaces the old rather than sitting beside it), takes out a reserve of **`max(64 KB, partition/8)`**, and grants the largest capacity that fits — **clamping with a loud log line naming both numbers**. The arithmetic is in `segment_index.h`, free of Arduino so `test_segment_index` can reach it.

  **The clamp exists because nothing is preallocated.** A device configured at 10000 would accept it, grow for about a week at the 60 s period, and only then run the filesystem out from inside `append()` — long after the change that caused it, on a board reachable only over the air. The history writer has already reboot-looped this board once, which is why the RTC strike counter exists; the fit check stops a full partition becoming the second occasion. **Mixed-size segments do not widen that window**, and the argument is worth writing down: a slot is never grown past the current geometry, so the peak on-disk total is `max(what the old segments hold, storageBytes(granted))` — the first was already on the partition and the second is what the fit check just verified against free space plus the first.

  **It clamps in memory and never rewrites `/config.json`**, so the operator's number stays stored and freeing space is all it takes to get the records back — a clamp that silently edited the document would destroy the intent it is refusing. That is why it must be visible somewhere durable: the boot line lives in the 8 KB rolling buffer this device overwrites within hours, so `/data.json` carries **`Status.History`** — `stored / capacity records`, plus `(config asked for N; X KB available, Y KB reserved)` while the reduction applies. Reported against CAPACITY, not the configured value, because a whole segment is dropped at once and the buffer touches capacity only in the moment before a rotation.

  **The reserve is three named consumers plus one proportional one.** `POST /spiffs/upload` writes `/upload.tmp` and renames, so both copies exist at once and it refuses outright when the incoming size exceeds free space — the largest asset is `bootstrap.css.gz` at 29 899 B, and that endpoint is the recovery path letting ONE web asset be replaced without the filesystem OTA that overwrites `/config.json`. The `/log0..3.txt` backups are append-only within a boot and **nothing truncates them** (`Logger::backup()` opens `FILE_APPEND` hourly), so their size is bounded by uptime alone — measured 2026-09-04 by fetching all five over `/spiffs/` on 6224: **8 289 bytes** total, ~2 KB per boot, with `current.txt` at 1 byte fifteen seconds after a reboot. LittleFS is copy-on-write and cannot write at all without a free block, including the writes that would free space. The `partition/8` term covers the part that really scales: an allocator hunting free blocks in a partition run down to its last one.
- **`/history.json` caps a response at 200 records** (`g_historyMaxResponse`). 1440 records is 57 KB of raw struct and roughly 170 KB rendered as JSON, more than half this chip's DRAM with WiFi already holding a share. The handler keeps a `static IoRecord buffer[200]` — 9.6 KB of DRAM, visible in the build.
- **`forEach()` walks in ABSOLUTE coordinates**, not logical ones. It releases the mutex every 64 records so a daily training run does not block `async_tcp` for seconds, and a rotation landing in that gap shifts every logical index by a whole segment — 180 records, where the ring shifted by one. The walk tracks the ordinal since the first append ever and subtracts `evicted()`, so a rotation costs exactly the records it discarded.
- **The index arithmetic lives in `include/core/segment_index.h`**, free of Arduino and LittleFS so `test_segment_index` can reach it. A wrong answer there reorders history instead of failing — including that `counts` is indexed by SLOT while `order` lists slots, a confusion that gives right answers until the first rotation and wrong ones forever after.

## The boot-loop interlock

The history writer has already reboot-looped this board once, and recovering needed `POST /config.json` — which needs the device to stay up long enough to answer. A config key cannot guard against that, because a config change only takes effect at the NEXT boot: turning history back on and being wrong leaves a device that panics before it can be told otherwise, and with no USB attached that is unrecoverable.

So the strike count lives in **RTC memory** (`RTC_NOINIT_ATTR`), which survives a panic reset and not a power cut. Three consecutive boots ending in a panic or a watchdog and `setup()` refuses to start the writer, logs why, and lights the error blink — leaving `history.records` untouched, so a clean power cycle is a fresh attempt. `historyTaskHandler()` clears the count once it has been running ten minutes, which a writer that crashes on its first append never reaches.
